    Ponytail 是什么？

    Ponytail 是一个 AI 代理行为强化工具。它不教你怎么写代码，而是教你的 AI 助理什么时候不写代码。 它内置了一套决策阶梯，AI 在写任何代码之前都会依次检查 7 个问题——停在第一个成立的台阶上。

    🔑 核心洞见

    "Lazy about the solution, never about reading."——Ponytail 在 理解问题之后 运行。它先完整阅读受影响的代码、追踪真实流程，然后才用阶梯决定怎么写。验证、安全、可访问性这些绝不裁剪。

    打个比方：你让两个开发者"给这个 API 加个缓存"。普通 AI 直接写了 50 行 Redis 缓存代码。用了 Ponytail 的 AI 会先想："等等，这个 API 一分钟才被调用 3 次，真的需要缓存吗？"——然后告诉你不需要，省了 50 行代码和一套 Redis 依赖。

    Ponytail 本身是一个插件包，包含一组规则文本和一个轻量级运行时。它通过宿主工具的插件系统（或直接复制规则文件）注入到 AI 的行为指令中。安装后，每次 AI 响应时，这些规则就像"写在脑子里的操作手册"一样自动生效。

    7 级决策阶梯

    Ponytail 的核心机制就是这个阶梯。每次 AI 打算写代码，都会先走一遍：

    层级问题结果代码量
    1这东西真的需要存在吗？→ 跳过（YAGNI 原则）0 行
    2代码库里已有实现？→ 复用现有代码0 行
    3标准库能实现？→ 不加外部依赖0 行
    4平台原生功能？→ 用浏览器/OS API0 行
    5已安装的依赖能实现？→ 不再加新依赖0 行
    6一行能搞定？→ 只写一行代码1 行
    7以上都不行→ 写最小可用代码尽量少

    前 6 级都是在避免写新代码。只有到第 7 级，AI 才会真的动手写。这个阶梯在脑中跑起来大致是这样的逻辑：

    // 每次写代码前的"内心独白"
function decideWhatToWrite(request) {
  // 1. 先理解问题——阅读受影响代码、追踪数据流
  read(request.affectedFiles);

  // 2. 走阶梯
  if (!needed(request))         return "跳过——这个功能其实不需要";
  if (existsInCodebase(request)) return "复用已有的：" + findExisting(request);
  if (stdlibCanDo(request))      return "用标准库：" + findStdlibApi(request);
  if (platformNative(request))   return "用平台原生：" + findNativeApi(request);
  if (existingDepCanDo(request)) return "用已有依赖：" + findExistingDep(request);
  if (oneLineCanDo(request))     return writeOneLine(request);

  // 3. 最后才写最小可用的代码
  return writeMinimalCode(request);
}

    四种模式详解

    Ponytail 的激进程度可以调节，适合不同场景：

    模式力度适合场景一句话
    lite🌱 温和写原型、探索阶段，不想被约束"少一点就好"
    full⚡ 标准日常开发（默认模式）"写该写的代码"
    ultra🔥 激进重构臃肿代码、"代码库得罪你了""这行真的需要吗？"
    off🔌 关闭需要大量样板代码的场景（如 API 客户端生成）"别拦我"

    切换命令直接在会话中敲就行：

    /ponytail        # 查看当前模式
/ponytail full   # 切换到标准模式
/ponytail ultra  # 切换到激进模式
/ponytail lite   # 切换到轻量模式
/ponytail off    # 关闭 Ponytail

    每次会话启动和模式切换时，Ponytail 都会在终端显示当前模式，让你知道它处于什么状态。

    安装到 Claude Code

    安装只需要两条命令，分两次发送：

    /plugin marketplace add DietrichGebert/ponytail
/plugin install ponytail@ponytail

    安装后会注册两个生命周期钩子（在 /hooks 中可见）。建议信任它们，以便 Ponytail 正常工作。下次新会话起，Ponytail 就会自动激活。

    如果之后想卸载：

    /plugin remove ponytail

    卸载后可以运行 node scripts/uninstall.js 清理残留的状态文件（注意：需在卸载插件前运行该脚本，因为脚本本身属于插件文件）。

    配置与持久化

    Ponytail 支持多种配置方式，按优先级从高到低：

    1. 运行时切换：/ponytail ultra 临时生效，当前会话有效
    2. 环境变量：设置 PONYTAIL_DEFAULT_MODE 指定默认模式
    3. 配置文件：在 ~/.config/ponytail/config.json 中写入设置

    环境变量方式适合在终端配置文件中永久设置：

    # PowerShell profile.ps1
$env:PONYTAIL_DEFAULT_MODE = "ultra"

# 或控制子代理的规则注入范围
$env:PONYTAIL_SUBAGENT_MATCHER = ".*test.*"   # 只对名称包含 test 的子代理生效

    配置文件方式（Windows 路径 %APPDATA%\ponytail\config.json）：

    {
  "defaultMode": "ultra"
}

    什么时候不用 Ponytail？

    Ponytail 不是万能的，有些场景反而不适合：

    • 生成大量样板代码——比如 API 客户端、DTO 类、ORM 模型。这些虽然"啰嗦"但是必要的，用 off 模式就好。
    • 学习/探索阶段——你还不熟悉一个库的 API 时，让 AI 写出完整示例比精简代码更有价值。用 lite 模式。
    • 写测试用例——测试需要显式覆盖各种边界情况，"精简"反而可能遗漏用例。不过 Ponytail 声明不裁剪测试覆盖率本身。
    • 安全敏感代码——Ponytail 明确不裁剪安全验证，但如果你不放心，可以临时 off。

    好消息是切换模式只需要一条命令，你完全可以在任务中随时调整。

    查看答案

    答案："这东西真的需要存在吗？"（YAGNI 原则）。大多数时候，功能根本不需要写——这是 Ponytail 最有效的一级。

    问题 2：Ponytail 和 Caveman 的区别是什么？

    查看答案

    答案：Ponytail 控制代码量（少写多余代码），Caveman 控制措辞（少说废话）。一个管"做什么"，一个管"说什么"，互不冲突，可以搭配使用。

    问题 3：小明想让 Claude Code 帮他重构一个老项目。他应该用什么模式？

    查看答案

    答案：ultra 模式。重构老项目时，代码库往往有很多冗余代码，ultra 模式会最激进地精简——"代码库得罪你了"就是为这种场景设计的。
