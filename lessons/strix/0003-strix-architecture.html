    架构与原理

    多 Agent 编排与自动修复

    前两课你学会了 Strix 怎么用。这课深入它是怎么工作的——多 agent 图编排、沙箱隔离、真实 PoC 验证、自动修复生成。 理解架构后你就能更好地配置和扩展它。

    Graph of Agents 架构

    Strix 的核心是一个多 agent 图编排系统——不同专长的 AI agent 组成一个有向图，协作完成渗透测试。 

    你的应用（代码 / URL）
     ↓
┌─ 侦察 Agent ────────┐  子域名枚举、指纹识别、端点发现
│  Recon Agent         │  扫描攻击面
└─────────┬───────────┘
          ↓ 共享发现
┌─ 注入测试 Agent ────┐  SQL/XSS/命令注入测试
│  Injection Agent     │  基于侦察结果定向测试
└─────────┬───────────┘
          ↓ 共享发现
┌─ 验证 Agent ────────┐  生成 PoC 验证漏洞
│  Validation Agent    │  不是假阳性，是真的能复现
└─────────┬───────────┘
          ↓
┌─ 报告 Agent ────────┐  生成报告 + 自动修复 PR
│  Report Agent        │  CVSS 评分 + OWASP 分类
└──────────────────────┘
    💡 和 Claude Code Workflow 的相似之处

    你在 CC L4 学的 workflow 也是多 agent 编排——只是 Strix 把它用在了渗透测试领域。

    Strix 的 Graph of Agents 相当于一个专为安全测试设计的 workflow，agent 之间共享发现、动态协调。

    沙箱隔离

    所有 agent 活动都在 Docker 沙箱中执行：

    组件作用
    HTTP 拦截代理 (Caido)拦截和修改请求/响应
    浏览器自动化测试 XSS、CSRF、点击劫持
    Python 运行时执行自定义利用代码
    Shell 终端命令执行和系统操作

    沙箱确保：本地处理，数据不发送到外部——你的代码和流量只在沙箱内流动。

    真实 PoC 验证

    Strix 与传统扫描器的最大区别：每个发现都经过验证。

    传统扫描器Strix
    检测方式规则匹配AI 动态分析
    结果可能有假阳性可工作的 PoC
    验证人工复查自动验证
    修复手动修复AI 生成修复 PR

    自动修复

    Strix 不仅能发现问题，还能生成修复代码——作为可直接合并的 Pull Request：

    漏洞发现 (SQL注入)
  → AI 分析根因
  → 生成修复代码（参数化查询）
  → 创建修复 PR
  → 你只需审核合并

    持续学习

    Strix 在多次扫描间积累经验：

    • 适应代码库 — 理解项目的架构和常见模式
    • 减少误报 — 从过去的误报中学习
    • 共享上下文 — 多个 agent 之间共享发现的上下文

    动手练习

    🎯 对比测试

    1. 准备一个有漏洞的测试项目

      用 DVWA（Damn Vulnerable Web Application）或 Juice Shop 跑一个本地实例。

    2. 用传统扫描器先扫

      比如 nikto 或 zap 扫同一目标，记录结果。

    3. 用 Strix 扫
      strix --target http://localhost:8080
    4. 对比差异

      比较两边的发现数量、假阳性率、可操作性。
