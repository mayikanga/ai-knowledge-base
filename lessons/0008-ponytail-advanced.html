    Ponytail 进阶

    Review 审查、Audit 审计、Debt 追踪、Caveman 搭配、子代理规则

    Mission 关联：第一课你学会了 Ponytail 是什么、怎么装、四种模式怎么切换。这一课把这些知识变成日常习惯——在真实项目中使用 review/audit/debt 三个核心命令，搭配 Caveman 控制输出措辞，并让子代理也继承精简规则。

    /ponytail-review：审查当前更改

    这是你日常最常用的命令。写完代码后跑一遍，Ponytail 会分析当前 diff，找出可以精简的部分。你不需要切换模式——review 会自动使用当前模式的标准来判断。

    /ponytail-review

    它的工作原理是：读取当前所有未提交的更改（相当于 git diff 的范围），逐段检查是否有更简洁的实现方式。输出是一份清单，列出每处可精简的位置和建议：

    📋 Ponytail Review — 3 处可精简

1. src/api/users.py:45-52
   `validate_email()` 函数：标准库 email-validator 已实现
   → 建议替换为 from email_validator import validate_email

2. src/services/cache.py:12-30
   `get_cached_user()` 函数：此 API 调用频率 < 1次/分钟
   → 建议移除缓存层，直接查询数据库

3. src/utils/format.py:5-8
   `format_date()` 函数：datetime.strftime 原生支持
   → 建议删除此函数，直接调用 .strftime("%Y-%m-%d")

    每条建议都标注了文件名和行号，方便你直接定位。建议分为三类：

    建议类型含义通常怎么处理
    🟢 安全精简标准库或已有代码已覆盖，删除不影响功能直接删除或替换
    🟡 可优化代码可以更简洁，但改动需要验证评估后决定，可加 ponytail: 标记推迟
    🔴 需谨慎建议精简幅度大，可能影响其他模块仔细审查依赖关系后再改
    💡 最佳实践

    写完一个功能模块后，在提交前跑 /ponytail-review。把 review 结果过一遍，确认每一条——有些建议可能不适合你的场景，但大部分能帮你省下不必要的代码。养成习惯后，提交的代码质量会有明显提升。

    /ponytail-audit：仓库全面审计

    当你接手一个老项目，或者感觉代码库越来越臃肿时，用 audit 做一次全面体检。它会扫描整个仓库，不只是当前改动：

    /ponytail-audit

    建议在 ultra 模式下跑 audit，得到最激进的精简建议，然后筛选出真正值得改的部分。

    review 和 audit 的核心区别：

    对比维度reviewaudit
    扫描范围当前未提交的 diff整个仓库
    使用时机每次提交前定期维护 / 接手项目时
    输出量几条到十几条可能几十上百条
    建议操作立即修改分批处理，排优先级
    运行频率高频（每天多次）低频（每周或每月）
    ⚠️ 注意：audit 输出可能很多。建议按目录分批处理——先修核心模块，外围代码可以打上 ponytail: 标记以后再说。不要试图一次性修复所有问题。

    /ponytail-debt：技术债追踪

    有时候你想精简某段代码，但当时没时间改——Ponytail 允许你在代码中标记技术债，以后统一处理。标记方式是写 ponytail: 开头的注释：

    // 在代码中标记技术债
def old_api_handler(request):
    # ponytail: 这个函数可以用 FastAPI 的依赖注入简化
    # ponytail: 等 v3 重构时一起处理，当前保持兼容
    return legacy_format(request)

// 另一个例子
class UserReport:
    # ponytail: 这个类 90% 的代码可以用 Pandas 的 groupby 替代
    # ponytail: 但下游有 3 个模块依赖这个类的接口，改之前要统一重构
    ...

    标记语法支持：// ponytail:（JS/TS/C#）、# ponytail:（Python/Ruby/YAML）、-- ponytail:（SQL/Lua）、<!-- ponytail: -->（HTML）。任何注释格式都可以，只要包含 ponytail: 前缀。

    之后在任何时候运行汇总：

    /ponytail-debt

    它会扫描所有 ponytail: 注释标记，按文件汇总成一份待办清单：

    标记位置技术债说明
    src/api/handlers.py:15可以用 FastAPI 依赖注入简化
    src/api/handlers.py:16等 v3 重构时一起处理
    src/utils/helpers.py:4290% 代码可用 Pandas groupby 替代
    🔑 关键用法

    写 ponytail: 标记时尽量说清楚"为什么没改"和"什么时候改"。# ponytail: v2 迁移后再精简，当前保持兼容 比 # ponytail: 待优化 有用得多。每个月初跑一次 /ponytail-debt，看看积压了多少技术债，决定哪些该在本月还掉。

    与 Caveman 搭配使用

    Caveman 是和 Ponytail 互补的工具。两者的分工很清楚：一个让 AI 少写代码，一个让 AI 少说废话。

    PonytailCaveman
    控制对象AI 写的代码AI 输出的文字
    解决什么问题不必要的代码过度详细的解释
    典型效果代码量 -54%输出减少 60-80%
    是否冲突不冲突。"Different halves, no overlap"——作者原话

    可以同时安装两者。Caveman 的安装方式和 Ponytail 类似：

    /plugin marketplace add <caveman-repo>
/plugin install caveman@caveman

    两者同时生效时效果很直观：你问一个问题，Caveman 让 AI 只给你最重要的答案（而不是三段式背景介绍+分析+总结），Ponytail 让 AI 写最少量的代码来实现。最终效果就是——"一句话回答问题，一行代码解决问题"。

    如果你觉得 AI 太啰嗦但代码量还可以，只装 Caveman。如果你觉得代码太臃肿但解释还行，只装 Ponytail。两者互相独立，互不影响。

    子代理规则注入

    默认情况下，Ponytail 的规则会注入到所有子代理中。这意味着你启动的 @code-reviewer、@docs-writer 等子代理也会继承精简规则。

    你也可以通过环境变量精细控制：

    # 只对名称含 test 的子代理生效
$env:PONYTAIL_SUBAGENT_MATCHER = ".*test.*"

# 不让任何子代理继承 Ponytail
$env:PONYTAIL_SUBAGENT_MATCHER = "a^"

# 不设置（默认）：所有子代理都继承

    匹配规则基于子代理的定义文件名（agent 的 name 字段）：

    子代理名称匹配 .*test.*是否注入规则
    test-runner✅ 匹配是
    code-reviewer❌ 不匹配否
    integration-test✅ 匹配是

    子代理默认继承主会话当前的模式（full/ultra/lite/off）。如果你想在子代理中用不同模式，可以在子代理启动时指定。

    动手练习：完整工作流

    🎯 练习：用 Ponytail 走一遍日常开发流程

    场景：你在一个项目里刚写完一个新功能，现在用 Ponytail 全套工具做一遍代码精简。如果你手头没有现成的项目，可以创建一个临时文件写一段代码来练习。

    1. 写代码——打开任意项目，写一个简单的函数（比如读取 CSV 做数据统计），或者用你现有的未提交改动
    2. Review——运行 /ponytail-review，查看 Ponytail 建议了哪些精简。至少采纳一条建议，然后再次 review 确认修改生效
    3. 标记技术债——在一条暂时不动的代码上加上 # ponytail: 之后重构 注释，运行 /ponytail-debt 确认它出现在待办清单中
    4. 模式对比实验——先后用 full 和 ultra 模式跑同一个请求，观察 AI 输出的代码差异有多大。ultra 模式会不会剪掉太多？
    ✅ 本节要点
    • /ponytail-review — 提交前审查当前 diff，养成习惯
    • /ponytail-audit — 全面审计整个仓库，建议 ultra 模式 + 分批处理
    • /ponytail-debt + ponytail: 标记 — 追踪推迟处理的技术债，月初跑一次
    • Caveman 控制"说"，Ponytail 控制"做"，互不冲突可同时安装
    • PONYTAIL_SUBAGENT_MATCHER — 精细控制哪些子代理继承精简规则
